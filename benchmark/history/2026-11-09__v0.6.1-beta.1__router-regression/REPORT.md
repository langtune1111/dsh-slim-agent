# 一次「优化」把 PASS 从 14 打回 9（0.6.1-beta.1）

> Qwen3.5 4B / 64K / 思考关

---

## 1. 事故经过

0.6.0-alpha.1 拿到 **14/36 PASS**（A/B/C 三类首次出现通过）。
审计时我加了一个「已经检索过就不再注入路由段」的守卫，理由是省上下文：

```js
const alreadySearched = (searchBudget.get(key) ?? 0) > 0
if (timeSensitive && !alreadySearched) { 注入路由段 }
```

结果全量重跑：**9/36 PASS，A/B/C 三类全部归零。**

| 版本 | PASS | A | B | C | D | T |
|---|---|---|---|---|---|---|
| 0.6.0-alpha.1（无守卫） | **14/36** | 2 | 1 | 1 | 6 | 4 |
| 0.6.0-beta.1（有守卫） | 9/36 | 0 | 0 | 0 | 5 | 4 |

## 2. 原因

路由段不是「开局提醒一次」就够的东西。模型第一步搜索完，第二步就看不到
「答案在网页上、不要翻工作区」这句话了，于是**立刻退回 bash 翻空目录**，
把剩下的步数耗光，最后交一个「未证实」。

## 3. 处理

把守卫撤掉，路由段**每一步都注入**。撤掉后立刻复测：

| A1/A2/B3 各 2 次 | PASS 3/6 | 平均搜索 3.0 次 |

A1 恢复 2/2 全对。

## 4. 教训

**上下文里每一条约束都要考虑「它消失之后模型会怎么走」。**
这次省下来的那点上下文，代价是 5 个 PASS。留着 `lastUserText` 的限长与会话清理（那是纯资源问题），
但「不要重复唠叨」这种面向人类的直觉，在 4B 模型上不成立。
