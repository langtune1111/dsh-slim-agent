## 1. 三个补跑包

| 包 | 内容 | 运行数 | 预估耗时 | 能补上什么 |
|---|---|---|---|---|
| **P2-A** | 补 6 道未跑主线题 × 7 arm × 2 模型 × 1 重复 @64K | **84** | ~2.5 h | 12 道主线题全覆盖，四类任务各有 2–3 题 |
| **P2-B** | 3 道超纲题 × 7 arm × 2 模型 × 1 重复 @64K | **42** | ~1.2 h | 能力天花板证据（预期接近 0，但可标出失败类型分布） |

## 2. 每包的验收口径

所有包复用同一套判据（见 `dataset.json` 与 REPORT §3），额外要求：

1. **P2-A 完成后**，报告 §4.1/4.4 必须能按四类任务出满 3 题/类的分母；
   若某类仍只有 1–2 题，需在报告里注明。
2. **P2-B 完成后**，超纲题单独成表，**即使 0/42 也要写**，并给出失败类型分布（`TOOL_LOOP` / `STALE_SOURCE` / `FAKE_CITATION`）。
3. **P2-C 只有在 `BUDGET_INVALID` 比例 < 10% 时才进主表**；否则只作为"DSH 预算算法缺陷"的证据，不计入通过率。
4. 任何一包跑完，`runs.ndjson` 只追加不覆盖，报告版本号与实验编号同步更新。

## 3. P2-C 的前置条件（4K 为什么现在不能跑）

`pi-ai` 的 `clampMaxTokensToContext()` 在算输出预算时**固定扣 4096 tokens**：

```js
const CONTEXT_SAFETY_TOKENS = 4096;
const available = model.contextWindow - estimateContextTokens(context).tokens - CONTEXT_SAFETY_TOKENS;
return Math.min(maxTokens, Math.max(MIN_MAX_TOKENS, available));
```

`contextWindow = 4096` 时 `available` 必然 ≤ 0，于是 `max_tokens = 1`。
第一轮实测：8K 下已有 8 次 `BUDGET_INVALID`；4K 会 100% 触发。

**三条可选路径**（按推荐排序）：

1. **等上游修**（issue 已备好：[ISSUE-dsh-context-budget.md](ISSUE-dsh-context-budget.md)）；
2. **本地临时绕过**：把 `contextWindow` 配成 8192 而把实际窗口当 4096 用——**不推荐**，会污染"4K 是否可行"的结论；
3. **只记录不比较**：跑 12 次，全部标 `BUDGET_INVALID`，作为缺陷证据而非性能数据。

**我的建议：P2-C 先不做**，等 issue 有回应。

## 4. 补跑之外，下一轮真正该改的东西

第一轮最硬的结论是"**没有一个 arm 拿到过引用合规**"——模型能搜到官方页面，但不把 URL 写回答案。
这不是工具数量问题，所以**不建议再加工具**。下一轮如果要动代码，只做一件事：

> 给 `web_search` 的输出加上强制回显字段（`[来源: <URL>]`），
> 并在 persona 里要求"**每个事实后面必须跟一个来源 URL**"，
> 然后**只测 `Citation Precision` 一个指标**，看这条约束能不能把小模型的引用率从 0 拉起来。

这是个单变量实验，规模只需要 **1 题 × 3 arm × 2 模型 × 3 重复 = 18 次**，半天内能出结果。
