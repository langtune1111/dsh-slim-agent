## 1. 摘要

**结论先行：180 次运行、7 种配置、2 个小模型，严格口径下通过率只有 `0`。**

1. **没有一种配置能完成「带官方引用的联网事实核查」。** 1.7B 与 4B 都跨不过这道门槛，
   与用不用插件、开不开子代理无关。
2. **但「能不能跑完」差别很大**：完整 slim（E/F）平均 78 s 就收敛并给出答案；
   极简/标准（A/B）、无子代理 slim（C/D）、pi（G）大量卡在超时。
3. **子代理是唯一的防跑飞装置**：D（有搜索、无子代理）平均发起约 26 次搜索，
   而 E（有搜索 + 子代理）只有约 7 次——没有子代理时，搜索工具会被反复空转调用。
4. **引用合规全线为零**：没有任何一次运行给出官方域名 URL，搜到了也没把它写进答案。

## 5. 结论

1. **Q1–Q3 的严格答案都是「不成立」**：180 次运行里严格 PASS 为 0。
   因此「搜索带来多少提升」「slim 比极简强多少」「子代理提高多少」都无法用通过率回答——
   所有配置都停在能力门槛之下。这是一个如实但不好看的结果。
2. **能回答的是「代价」与「收敛性」**：完整 slim 把平均耗时从超时上限 120 s 压到 78 s，
   把搜索调用从约 26 次压到约 7 次；代价是每任务约 16 次 LLM 请求。
   也就是说，**插件在这个量级上买到的是「不跑飞」，不是「答得对」**。
3. **引用能力是当前最大短板**：模型能搜到官方页面，但不会把 URL 写回答案，
   导致 Search Compliance 与 Citation Precision 全线为 0。
   下一步该做的是结构化输出约束，而不是继续加工具。
4. **不建议在这种情况下继续扩大架构**。0.3.0 已经删掉了会吞答复的 `task_complete`；
   本轮又证明「多工具 + 子代理」对小模型的价值主要在收敛性，不在正确率。
