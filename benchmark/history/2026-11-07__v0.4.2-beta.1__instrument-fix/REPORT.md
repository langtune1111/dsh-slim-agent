# 测量工具修正 + 结论文本前置（0.4.2-beta.1）

> 模型 LFM3 1.7B / 64K / 思考关 / `convergeMode: hardCap` + `final_answer`
> 三组各 6 次（A1 / B3 / D1 × 2 轮）

---

## 1. 重大发现：之前的题被污染了

审计 harness 时发现 `run_task.py` **无条件**把 `fixtures/` 拷进每个任务的工作目录。
于是 A1（「Node.js 当前最新 LTS 是多少？」）的模型一进工作区就看到 `D1.md`，里面写着「锁定 v24.11.0」，
它就地抄这个版本号，根本不去看检索结果。

也就是说：**此前 851 次运行里，A / B / C 类「纯联网题」全部被本地文件干扰**，
测出来的不是联网能力，而是「会不会读目录」。这是测量缺陷，不是模型问题。

**修复**：改为按题投放——只有 `D1/D2/D3/T2` 才铺对应 fixture，其余题目工作区为空。

## 2. 本轮三组对照

| 组 | 配置 | 事实命中 | PASS | 说明 |
|---|---|---|---|---|
| A | 全部铺 fixture + 结论前置 | 2/6 | 2/6 | |
| B | 按题投放 fixture + 结论前置 | 0/6 | 0/6 | |
| C | 按题投放 + 只返回 1 条搜索结果 | 0/6 | 0/6 | |

## 3. 结果解读

1. **A 组的 2 次事实命中全是 D1 题**——它读的是本地 `D1.md`，不是检索结果。
2. **B 组（去掉干扰文件）反而 0 命中**：模型工作区空了，直接写「未证实」。
   说明它**从来没真正用上检索结果**，之前所谓「答对」是被本地文件喂出来的假象。
3. **C 组（只给 1 条结果）也是 0**：缩小选择面并不能让它提取事实。

**结论：1.7B 在「从检索摘要里提取事实」这一步上不可用。**
此前所有关于「搜索有没有用」的结论都要按这个前提重读。

## 4. 产品侧改动（很轻）

- `web_search` 结果顶部增加一行 `[S0] 结论候选：…`，把首条标题+摘要摊开，减少模型翻找成本。
- 结果里明确写「工作区文件里的版本号是历史记录，涉及当前/最新以检索结果为准」。
- persona 增加同一句约束。

## 5. 仍未解决

1. 事实提取能力（本轮的结论：该量级不具备）。
2. 引用几乎不出现。
3. 之前 851 次数据中 A/B/C 类题目的结果需要作废重跑。

## 6. 干净基线（去除污染后 12 次）

`A1 A2 B1 B3 C1 D1` × 2 轮，LFM3 1.7B / 64K / 思考关 / hardCap+final_answer

| 指标 | 数值 |
|---|---|
| 运行数 | 12 |
| PASS / FAIL / TIMEOUT | 1 / 11 / 0 |
| 调用 final_answer | 12/12 |
| 可读自然语言答复 | 12/12 |
| 任一事实命中 | 2/12 |
| 出现官方域名 | 1/12 |
| 平均搜索次数 | 1.1 |
| 平均耗时 | 57s |

**注意**：这一组里 TIMEOUT 是 0、平均耗时只有 57 秒，而历史数据动辄 180 秒超时。
差别不在模型，在于**工作区不再有干扰文件**——模型不再花几十步去翻目录，而是搜一两次就收尾。
这说明此前「74%-91% 超时」的结论同样被污染放大了。

## 7. 需要重跑的历史结论

- 851 次数据集里所有 A / B / C 类题目的 PASS / 事实命中 / 超时率——作废，需用修好的 harness 重跑。
- 唯一不受影响的是 D 类（本地+联网）与 T 类（Agent 基础），它们本来就需要 fixtures。
